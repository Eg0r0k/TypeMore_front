## СТЕЙДЖ 0 — диагностика (read-only, снята ДО любых правок)

### 0(а) Почему quote-ран не отправляется

**Это гейт по режиму вокруг сабмита — первый из трёх перечисленных вариантов.**
Сборщик payload при этом полностью готов к quote и НЕ возвращает undefined;
предусловия seed+dictHash нет.

Цепочка, дословно:

1. `src/features/run-submit/model/build-payload.ts:51`
   ```ts
   /** Ranked-eligible, seeded modes. `free` / `custom` / `quote` are never submitted. */
   export const RANKED_MODES = ['time', 'words'] as const
   ```
2. `src/features/run-submit/model/build-payload.ts:54-55`
   ```ts
   export const isRankedMode = (mode: GenerationMode): mode is RankedMode =>
     mode === 'time' || mode === 'words'
   ```
3. `src/features/run-submit/model/use-run-submission.ts:54`
   ```ts
   const eligible = ctx !== null && isRankedMode(ctx.mode)
   ```
4. `src/features/run-submit/model/submit-flow.ts:67`
   ```ts
   if (!gate.eligible) return set('ineligible')
   ```
   — возврат ДО `set('saving')` и до `deps.buildPayload()`, поэтому для quote
   запрос не уходит вовсе. Наблюдение владельца («для quote запрос не уходит»)
   подтверждается: это не 4xx и не отвал сети, это ранний return.

**Комментарий, объясняющий гейт как намеренный, есть** — строка
`build-payload.ts:50`, процитирована выше целиком. Она ставит `quote` в один ряд
с `free`/`custom`. Продуктовое решение из задания эту строку отменяет: `free` и
`custom` остаются неотправляемыми, `quote` — нет.

**Чего в гейте НЕТ (проверено, чтобы не чинить не то):**

- `buildRunPayload` (`build-payload.ts:93-126`) обрабатывает quote явно:
  `dimensionOf` (`:128-132`) возвращает `{}` для `mode === 'quote'`, а
  `generation.textSource` ужимается до `{ kind, quoteId, quoteHash }` без текста
  (`:96-101`). То есть switch, где `ModeQuote` не обработан, — НЕ наш случай.
- Предусловия «нужны seed+dictHash» тоже нет: у quote-рана оба поля есть и
  осмысленны — `seed` генерируется всегда (`src/pages/home/ui.vue:523`), а
  `dictHash` для quote равен `dictVersion([quote.text])`
  (`src/shared/core/words.ts:209-220`), т.е. хешу ТЕКСТА, а не словаря.
- Второй, независимый гейт на этой же странице —
  `src/pages/home/ui.vue:345-351` (`finishedOk`): `!race.racing &&
  !repeatedRun.value`. Он не про режим и quote-раны сам по себе не блокирует, но
  он же блокирует ПОВТОР той же цитаты (`onRepeat`, `:609-616` ставит
  `repeatedRun = true`) — а по продуктовому решению повтор одной цитаты
  нечестностью не является. Это второй объект правки в стейдже 4/3.5.

**Контракт цитаты уже существовал и уже был записан в docs рядом с сидовым
setup.** Ничего не выдумано, ничего не добавлено.

- **Хеш текста в схеме цитат ЕСТЬ** (`db/migrations/00007_quotes.sql:42`,
  `text_hash`), считается вендоренным бандлом через goja, а не Go/SQL-репликой.
  Останавливаться было не на чем.
- Резолв идёт по `(id, hash)`, а не по «текущей версии»: `GET /quotes/{id}`
  — единственное чтение, отдающее superseded-ревизии, именно чтобы ран,
  пересуженный после правки цитаты, не развалился.

**Что пришлось завести:** одно новое поле, и оно относится к стейджу 3.5, а не к
цитатам — `setup.adoptedFromRunId` (`docs/RUNS.md`, «Text provenance»).
Именование — по существующим соглашениям setup (camelCase, опционально,
отсутствие = легаси-форма).

**Проверка на commit-consistency и хеши/подписи setup:**

- подписей или хешей ПОВЕРХ документа `setup` в системе нет — grep по
  `setup_hash|signature|sha256(setup)` пуст; `bundle_sha` хеширует бандл, не
  сетап;
- `Core.Replay` (`internal/replay/core.go:430-473`) разбирает setup ровно на
  `config` / `generation` / `declaration` и собирает вход для ядра из них. Любой
  ЧЕТВЁРТЫЙ ключ верхнего уровня физически не доезжает до fold'а — поэтому
  `adoptedFromRunId` не может сдвинуть ни один таргет, ни метрику, ни score;
- commit-consistency (`src/shared/core/validate.ts:191`) — правило РЕДЬЮСЕРА о
  коммитах, ветвящееся на `nospace` из снапшота. К полям setup верхнего уровня
  отношения не имеет;
- поле НАМЕРЕННО не положено внутрь `generation`: `generation` едет в seed-контекст
  и участвует в реконструкции рана. Провенанс там был бы способом влиять на текст.

## СТЕЙДЖ 2 — бэк: резолв текста для ModeQuote

**Резолв уже был реализован целиком**, ровно по описанной дорожке:

`core.Replay` → `validateLog` → `scoreOfLog`/`scoreV2OfLog` из бандла, точное
равенство.

Отказы на месте и оба покрыты:
- цитата не найдена по id → `ErrUnknownQuote` → `flagged`, `reason:
  unknown_quote` (`internal/replay/decide.go:46`; тесты
  `TestQuoteRunOnAnUnknownQuoteIsFlaggedNotRejected`,
  `TestMalformedQuoteIDIsFlaggedAsUnknownQuote`);
- хеш не совпал → тот же жёсткий отказ (`worker.go:382`; тест
  `TestQuoteRunWithAMismatchedHashIsFlaggedNotRejected`).

Оба «жёсткие» в смысле «ран не судится и не получает чисел», но
**flagged, а не rejected** — это осознанное решение бэка, записанное в коде и в
`docs/REPLAY.md`: разошедшийся хеш говорит о том, какие байты держит ЭТА нода, а
не о том, что игрок печатал другой текст.

### Была ли нормализация местом расхождения — НЕТ

Это главный вывод стейджа, и он отрицательный по двум независимым причинам.

**(1) `normalize.ts` вообще не трогает текст цитаты.** Это ВХОДНОЙ адаптер: он
решает, какую графему СОХРАНИТЬ за нажатием (типографская кавычка, введённая
против прямой, записывается как ожидаемая). Его собственная шапка
(`src/shared/core/normalize.ts:20-25`) формулирует инвариант: «нормализация
происходит ДО того, как событие существует… меняет то, что ЗАПИСАНО, и никогда —
то, как что-либо судится: ядро, протокол и сервер остаются байт-в-байт теми же».
Ожидаемый текст не нормализуется никогда — значит, серверу нечего звать, и
переписывать на Go тоже нечего. `AUDIT_STATE` раздел 4.4 независимо это
подтверждает: `normalize.ts` не импортируется ни одним модулем ядра, и именно
поэтому его отсутствие в вендоренном бандле безвредно.

**(2) Место, которое РЕАЛЬНО могло разойтись — не нормализация, а токенизация**
цитаты: правило «каждый перевод строки переписывается в `"\n "`, затем split по
U+0020 с отбрасыванием пустых» (`src/shared/core/words.ts:332-356`). Оно живёт в
ядре, вендорено в бандл (`core.bundle.js:847-859`), и сервер зовёт именно его:
`setQuoteText` (`core.go:692`) сажает байты реестра на
`generation.textSource.text` ПАРСЕННОГО входа, после чего `generateWords`
бандла делает всю работу. Go-реализации токенизации в репозитории нет.

**Проверка текста раньше score — сделана и стоит первым тестом.**
Добавлено:
- `Core.QuoteTargets` (`internal/replay/core.go`) — таргеты цитаты, полученные
  тем же бандлом;
- `internal/replay/quote_targets_test.go`:
  `TestQuoteTargetsComeFromTheBundleAndNormaliseNothing` — 9 кейсов ЛИТЕРАЛАМИ,
  зеркалящих фронтовый пин `src/__tests__/core/quote-source.test.ts`. Три из них
  — ровно те символы, что названы в задании: типографские кавычки/апостроф,
  неразрывный пробел (НЕ разделитель и НЕ сворачивается в U+0020), тире трёх
  видов. Плюс узкий неразрывный пробел. Go-токенизатор, «причёсывающий» любой из
  них, роняет этот тест;
- `TestTheQuoteVectorsTextTokenisesToTheTargetsItWasPlayedOn` — на реальном
  golden-векторе.

Прогон: 9/9 PASS. Расхождения нет ни на одном символе.

## СТЕЙДЖ 3 — бэк: бакет, борды, TP

**Бакет, борды и пагинация уже были построены целиком** — хвост Stage C в

### Что оказалось свойством режима, а что пришлось заводить

**Свойством — всё, что нужно для бакета.** Ключ quote-бакета собирается не
перечислением режимов: правило целиком живёт в одном вью
`leaderboard_eligible_runs`, и координата там — `quote_id`, полученная из
`run_quote_id(setup)` и РЕЗОЛВНУТАЯ через `quotes`. Это свойство рана («его текст
— вот эта опубликованная цитата»), а не имя режима; сидовый ран на него не
отвечает, quote-ран не отвечает на языковую ветку. Существующее свойство
покрыло нужное поведение — заводить ничего не пришлось.

`protocol.IsCounted` (прецедент `lobbyEntryOf`) проверен и НЕ подошёл: это
свойство МАТЧА по WS («матч кончается концом текста, а не часами»), у него три
call-site в `internal/ws`, и к бордам ранов оно отношения не имеет.

**Пришлось завести — только провенанс текста** (`adoptedFromRunId`), стейдж 3.5.

### leaderboard_entries, sort_key, пагинация

- Лучший ран игрока на КАЖДОЙ цитате — было
  (`TestQuoteBoardKeepsOnlyThePlayersBest`).
- Пагинация прогнана на quote-бакете: добавлен
  `TestQuoteBucketPagesExactlyLikeALanguageBucket` — те же утверждения, что у
  языковой борды: порядок, разрыв ничьей по `achieved_at`, СЧИТАННЫЙ (не
  перенесённый в курсоре) ранг, и полный обход борды курсором с проверкой, что
  каждая строка встречена ровно один раз. PASS.

### Политика supersede против борды — ЗАПИСАНА И ЗАКРЕПЛЕНА, но формулировка задания требует поправки

Найденный факт: **supersede создаёт НОВУЮ строку с НОВЫМ id**
(`quotes_revision_idx` = `(lang, upstream_id, text_hash)`, `InsertQuoteRevision`
делает `gen_random_uuid()`). То есть **один id = один текст навсегда**, и пара
`(id, hash)` взаимно однозначна.

Отсюда две половины, и вторая расходится с текстом задания:

1. **«Борда ключуется на id цитаты, а не на (id, hash)» — верно, и это УЖЕ
   поверсионно.** Пара была бы избыточной: id определяет hash. Ран, вставший на
   борду, остаётся на ней против тех байтов, на которых играл, навсегда.
2. **«Правка опечатки борду НЕ сбрасывает» — верно для СУЩЕСТВУЮЩЕЙ борды и
   неверно для корпуса.** Правка не сбрасывает борду — она её ФОРКАЕТ: у
   исправленного текста другой id, значит другая, пустая борда, и игроки,
   вытянувшие цитату после правки, ранжируются там. Две популяции не сливаются.
   Утверждение задания «если цитату переписали содержательно — это новая цитата
   с новым id» на практике верно для ЛЮБОЙ правки, включая опечатку: реестр не
   различает эти случаи.

Записано в `docs/LEADERBOARDS.md` («Supersede versus the board») обеими
половинами. Закреплено тестами:
- `TestSupersedingAQuoteLeavesItsBoardAloneAndOpensANewOne` (4 подтеста);
- `TestARunJudgedAfterItsQuoteWasRetiredStillRanks` — ран, засуженный ПОСЛЕ
  ретайра ревизии, всё равно встаёт на борду (`superseded` не входит в join
  проекции);
- сквозной `TestASupersededQuoteLeavesAnAlreadyRankedRunAlone` (стейдж 6).

### TP — УПЁРЛОСЬ. Не чинил, докладываю

**TP в системе не существует.** Ни таблицы, ни формулы, ни пакета: `internal/rating/`
нет, grep по `tp_total|typing_points|TypingPoints` даёт только `ARCHITECTURE.md`
и `BACKEND.md`, где TP числится пунктом 6 нереализованной дорожной карты;
`SCORING_CONCEPT.md §8` ставит его последним («когда есть серверный пересчёт из
логов и хоть какая-то популяция игроков»). На фронте TP тоже нет — единственное
упоминание в `src/shared/core/score.ts:27` гласит «TP НЕ входит в scoreV2».

**Следствие:** требование «TP начисляется без исключений для quote» и тесты
«двигает TP» выполнить нельзя — двигать нечего. Ничего не выдумывал.

Что сделано вместо: **закрыт крючок, который иначе унаследовал бы отменённое
решение.** `db/migrations/00009` и `docs/LEADERBOARDS.md` прямо инструктировали
будущую реализацию TP считать `WHERE quote_id IS NULL`, то есть исключать
цитаты. Продуктовое решение задания это отменяет. Раздел в
`docs/LEADERBOARDS.md` переписан: TP считает ВЕСЬ `leaderboard_eligible_runs`
без дополнительного предиката — quote-раны дают TP наравне с сидовыми, а
seeded repeat'ы уже исключены самим вью. В `00009` править нельзя (применённая
миграция — история), поэтому опровержение стоит в шапке `00017`.

### Числа по бакетам при 15 817 цитатах

Корпус пересчитан на месте: 86 файлов, **ровно 15 817 цитат** — число из
задания сходится.

**Сколько бакетов появится.** Не 15 817. Борда существует только тогда, когда в
ней есть хотя бы одна видимая строка (`ListLeaderboardBuckets` — `GROUP BY` по
`leaderboard_entries`, пустые бакеты в каталоге просто отсутствуют). Верхняя
граница — 15 817 quote-бакетов; фактическое число = число сыгранных цитат.
Строк — не более `игроков × сыгранных цитат` (по одному слоту на игрока на
цитату).

**Как ложится на индексы.** Хорошо. `leaderboard_sort_idx (bucket_key, sort_key
DESC, achieved_at ASC, user_id ASC)` ведёт `bucket_key` первым, поэтому quote-борды
— просто новые значения ведущей колонки; чтение страницы остаётся одним range-scan
той же глубины, что у языковой борды, независимо от числа бакетов. `quote:<uuid>`
— 43 байта против ~20 у языкового ключа: +23 байта на строку индекса, шум.
`leaderboard_entries_run_idx` и `leaderboard_entries_user_idx` к форме ключа
безразличны.

**Где упирается — запрос списка борд.** `ListLeaderboardBuckets` (`queries.sql:149`)
— `SELECT bucket_key, count(*) FROM leaderboard_ranked GROUP BY bucket_key ORDER BY
bucket_key`, **без LIMIT и без курсора**. Комментарий в самом запросе это признаёт:
«Quote boards are in here alongside the language ones, and they are the reason this
result is no longer bounded by the schema». Языковых борд конечное число (2 режима ×
3 размера × языки); quote-борд — сколько сыграно. При широком охвате корпуса это
полный проход `leaderboard_entries` с агрегацией и отдача десятков тысяч строк
одним ответом на КАЖДЫЙ запрос каталога.

**Не чинил** (задание: «Если упирается — сказать, не чинить»). Что понадобится,
когда упрётся: пагинация каталога либо отдельная поддерживаемая таблица счётчиков
по бакетам. Фронт при этом уже не зависит от каталога для quote-борд — рейка ведёт
на борду через пикер, а `isQuoteBucketKey` валидирует ключ ПО ФОРМЕ, не по
членству в каталоге, — так что ограничить каталог языковыми бордами можно без
изменений на клиенте.

## СТЕЙДЖ 3.5 — зачёт гонок с pace/ghost-кареткой

### ВАЖНОЕ СЛЕДСТВИЕ, проверено первым: такой режим ЕСТЬ, правило работает сегодня

Задание предполагало, что правило может не дать эффекта ни разу. **Это не так.**

- «Гонка против рана» действительно применяет сетап целевого рана целиком,
  включая слова: `src/features/test/race/ui.vue:145-150` —
  `game.setup({ config, words: data.words, generation, declaration })`.
  AUDIT A2 верен. Каждая ТАКАЯ гонка — seeded repeat.
- Но каретка по темпу поверх СВЕЖЕГО сида существует и построена:
  `src/features/test/pace/model/use-pace-caret.ts`. Режимы `pb` / `last` / `avg`
  / `custom` (config `paceCaret`) гонят бота с фиксированным wpm по словам
  ТЕКУЩЕГО рана — то есть ровно «каретка, идущая по темпу личного рекорда на
  новом тексте» из формулировки задания. `pb` резолвится против PB-бакета
  текущих настроек (`:130-145`). Это отдельная фича от гонки-с-призраком, она
  не трогает payload вообще и раньше молча запрещала рану… ничего: раны с
  pace-кареткой всегда отправлялись.

**Вывод:** правило вступает в силу немедленно и не является отложенным. Ничего
выдумывать не пришлось.

### Реализация — признак происхождения, а не отрицание по режиму

- **setup**: `adoptedFromRunId` — canonical uuid рана, у которого взят текст.
  Верхний уровень setup, не внутри `generation`.
- **бэк**: `run_adopted_from(setup)` + одна строка в
  `leaderboard_eligible_runs` (`AND run_adopted_from(r.setup) IS NULL`).
  Одно место — значит проекция, rebuild и все чтения не могут разойтись, и
  правило автоматически действует на ОБЕИХ формах борды. PB читает
  `leaderboard_entries` напрямую (`internal/profile/queries.sql:154`), поэтому
  исключается тем же изменением. TP, когда появится, читает то же вью.
- **приём**: `422 invalid_adopted_from` на всё, что не canonical uuid.
- **история**: `adoptedFromRunId` поднят в derived-ячейки `GET /runs`.
- **фронт**: правило вынесено в `src/features/run-submit/model/text-origin.ts`
  (`adoptedFromOf`, `isUnnameableRepeat`); `pages/home` его ЗОВЁТ.

Почему клиентскому непроверяемому полю здесь можно верить: оно умеет только
ОТНИМАТЬ зачёт у собственного отправителя. Подделка стоит своего места на борде и
не может его выиграть. Обратное написание («этот ран честный, свежий») подделывать
было бы выгодно — поэтому флаг сформулирован как обременение, а не как разрешение.

### Два дефекта, которые нашли собственные тесты

1. **Undashed uuid проезжал сквозь приём.** `uuid.Parse` принимает `{…}`,
   `urn:uuid:…` и форму без дефисов; SQL (`run_adopted_from`, `run_quote_id`)
   матчит ДЕФИСНЫЙ паттерн и на остальное отвечает NULL. То есть маркер без
   дефисов — это «маркера нет» ниже по течению, и seeded repeat молча
   засчитался бы. Введён `isCanonicalUUID`; **та же дыра закрыта для
   `textSource.quoteId`** — там зеркальная беда: воркер (uuid.Parse) цитату
   резолвит, вью — нет, и ран судился бы против цитаты, не попадая ни на одну
   борду. Добавлены 3 кейса в `TestIngestQuoteRunRefusesAnUnusableReference`.
2. **Неверный код ошибки на неправильный JSON-тип.** Число/объект в
   `adoptedFromRunId` роняли разбор всего конверта и отдавали
   `invalid_text_source`. Поле сделано `json.RawMessage` и разбирается отдельно.

### Честные ограничения

1. **Соло-повтор СИДОВОГО текста по-прежнему гейтится на клиенте, а не
   «сохраняется незасчитанным».** Ему нечего назвать: текст пришёл из
   предыдущей попытки самого игрока, которая могла вообще не отправляться и не
   иметь id. Отправить его БЕЗ маркера — значит засчитать, то есть дать
   единственный неверный ответ. Чтобы довести до «сохранён ≠ засчитан»,
   маркеру нужна форма «повтор, происхождение назвать нечем» — это изменение
   контракта, за которое я не брался. Записано в `text-origin.ts`.
2. **Повтор ЦИТАТЫ теперь отправляется** (раньше блокировался тем же
   `repeatedRun`). Это прямое следствие продуктового решения №1 («игрок может
   набирать одну и ту же цитату сколько угодно»): каждый ран на quote-борде
   по построению повторяет тот же текст — это ПРЕДПОСЫЛКА борды, а не изъян
   рана на ней.
3. **Раны гонок теперь попадают в профильные агрегаты.** Они `accepted`, а
   `GetProfileCounts` / `GetProfileMetricStats` считают по всем принятым ранам,
   не по ранжируемым. То есть `tests_completed` и средний wpm теперь включают
   гонки. Раньше их не было вовсе (не отправлялись). Менять семантику
   профильных агрегатов — за рамками задания; выношу на решение владельца.

## СТЕЙДЖ 4 — фронт: снять гейт

Причина из стейджа 0 убрана. `isRankedMode` / `RANKED_MODES` / `RankedMode`
удалены; на их месте `isSubmittableRun(ctx)` — **условие по свойству**:

```ts
function dimensionOf(ctx) {
  if (quoteOf(ctx.generation) !== undefined) return {}      // цитата: НИ ОДНОЙ размерности
  if (ctx.mode === 'time')  return { durationMs: … }
  if (ctx.mode === 'words') return { wordCount: … }
  return null                                                // размерности нет ⇒ борды нет
}
export const isSubmittableRun = (ctx) => dimensionOf(ctx) !== null
```

Одна функция — и гейт, и поле payload, поэтому они не могут разойтись (тот же
приём, что `emitsRawTokens` в ядре: «один предикат, два вызывающих»). Ветка
цитаты спрашивает ЯДРО (`quoteOf`) о разрешённом источнике текста, а не имя
режима — и это не косметика: `mode: 'quote'` без `textSource` вырождается в
сидовый word-count путь в `generateWords`, так что имя режима действительно не
решает. Такой ран теперь отбивается на клиенте, а не улетает за `422
invalid_dimensions`.

`free` / `custom` остаются неотправляемыми — у них нет размерности, значит нет и
координаты борды.

Поля стейджа 1 кладутся: quote-ветка `build-payload` уже клала
`{quoteId, quoteHash}` без текста; добавлен `adoptedFromRunId`.

**Тесты:**
- quote-ран уходит в POST /runs с корректным setup —
  `build-payload.test.ts` → «accepts a quote run», «emits quoteId + quoteHash,
  strips the text, and carries no dimension»; сквозной
  `TestQuoteRunIsJudgedAndLandsOnItsOwnBoard`.
- **payload сидового рана побайтово не изменился** — закреплено:
  «emits a byte-identical body for a seeded run (no textSource anywhere)»
  (`toEqual` на всё тело) плюс новый «omits the marker entirely when the text was
  generated fresh» (`Object.keys(setup)` = ровно три половины снапшота).
